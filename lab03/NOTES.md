Наблюдение: умножение снова появляется; файл соответствует последнему коммиту.

# NOTES: теги и версии (пункт 5)

## git tag -a v1.0 -m "Рабочая версия калькулятора"
Создаёт аннотированный тег v1.0 на текущем коммите.  
Наблюдение: тег закрепляет конкретную версию проекта и не двигается со временем.

## git show v1.0
Показывает метаданные и изменения, связанные с тегом.  
Наблюдение: видно, на какой коммит ссылается тег, кто и когда его поставил, и какие изменения были в этом коммите.

## git push origin v1.0
Отправляет тег на удалённый репозиторий GitHub.  
Наблюдение: теперь тег v1.0 виден и на GitHub, а не только локально.

## Чем тег отличается от ветки

| Характеристика | Ветка (branch) | Тег (tag) |
| --- | --- | --- |
| **Назначение** | Для активной разработки; указатель на последний коммит в ветке. | Для маркировки важных версий (релизов); «замороженная» точка в истории. |
| **Поведение** | Движется вперёд при новых коммитах. | Не двигается; всегда ссылается на один и тот же коммит. |
| **Когда использовать** | Когда продолжаешь работать над функционалом. | Когда выпускаешь стабильную версию (v1.0, v1.1 и т.д.). |
| **Пример** | `main`, `feat/division` | `v1.0`, `v1.1`, `release-2024-10` |

Вывод: ветки нужны для потока работы, теги — для фиксации значимых состояний. В этом задании мы закрепили рабочую версию калькулятора тегом v1.0.

# NOTES: отмена ошибочного коммита (пункт 4)

## git revert HEAD
Команда `git revert HEAD` создаёт новый коммит, который отменяет изменения последнего коммита.  
Наблюдение: в истории появились два коммита: ошибочный и его отмена. Код вернулся к безопасному состоянию (с проверкой на ноль или без деления).

## Чем git revert отличается от git reset --hard

| Характеристика | git revert | git reset --hard |
| --- | --- | --- |
| **Что делает** | Создаёт новый коммит-«антидот», который отменяет изменения. История остаётся линейной. | Перематывает указатель ветки назад и **удаляет** последующие коммиты из истории. |
| **Влияние на историю** | История сохраняется полностью; видно, где была ошибка и как её исправили. | История переписывается; «стёртые» коммиты исчезают (если не сохранены отдельно). |
| **Безопасность при публикации** | ✅ Безопасно использовать даже для уже отправленных (pushed) коммитов. Другие разработчики просто подтянут новый коммит отмены. | ❌ Опасно для опубликованных веток: придётся делать принудительный push (`push --force`), который ломает историю у других участников. |
| **Когда использовать** | Когда коммит уже есть в удалённом репозитории или его видели другие. | Только для локальной истории, которую ещё никто не видел (например, случайно закоммитил тестовый файл). |

Вывод: `git revert` — это безопасный способ исправить ошибку в общей истории. Он оставляет прозрачную запись: «была ошибка, вот она, и вот как мы её исправили». `git reset --hard` используют только для локальных исправлений до публикации. В этом задании мы использовали `revert`, потому что это правильный подход для совместной работы и публичных репозиториев.
